## Proposed CRM Data Architecture

* Master database for shared data across all departments
  1. Contact details, emails, URLs, product purchase amounts
* Department-specific databases branching from master:
  1. Sales: leads, contact history, call summaries, next-contact dates
  2. Marketing: outreach lists, form responses
  3. Finance: confirmed-sale records
  4. Customer Success: post-sale service data
* Data flows sequentially across departments:
  1. Marketing collects responses via website form
  2. Positive responses passed to Sales
  3. Confirmed deals passed to Finance
  4. Completed payments handed to Customer Success
* Compressed leadership view proposed: timeline of key events per company (purchase date, billing frequency, renewal status) visible to department leads and CEO

## LLM Usage Guidance (Hardeep)

* LLM is a lookup table: more context = more precise output
* Hardeep's own workflow: daily scheduled job transcribes all meetings, extracts project updates into per-project markdown files; feeds that file as context for any new task
* Key principle: define the work precisely before prompting
  * One sentence → LLM uses its own assumptions
  * Detailed document → LLM builds exactly what you specified
* Treat LLM as an assistant, not a master
  * Give it constraints and guidelines; let it take technical decisions within those bounds
  * Always be able to explain what the LLM built
* Hiring context: companies now test LLM control, not just coding ability
  * Interviewers check if candidates can explain and direct LLM output, not just generate it
* Technical decisions are mostly business decisions in disguise
  * Example: "real-time dashboard" question becomes "does the CEO actually need it updated more than every 5-7 minutes?"
